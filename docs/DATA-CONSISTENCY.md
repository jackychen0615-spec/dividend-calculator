## 規則 1：每檔標的的權威值，只有一個來源

**`articles/<代號>-dividend-calculator.html` 自己頁面上的表格，是該標的的唯一權威值。**
`functions/api/etf-dividends.js`、`compare.html`、任何比較頁、任何自動更新腳本產生的數字，
**都必須跟該標的自己的 `-dividend-calculator.html` 頁面對齊，不是反過來。**

為什麼是這個方向而不是 API：
- API 目前的資料來源/計算邏輯不明確，過去查到至少 7 檔 ETF（0050/0056/00878/00713/00939/00918/006208）跟自己主頁對不上
- 各標的主頁的表格是排程任務長期在維護、有「最後更新」日期的，可信度比 API 高

**如果你要改一個標的的配息/殖利率數字，改完之後務必回頭檢查：**
```bash
# 用這支腳本比對 API 跟各主頁是否一致（唯讀，不會自動改檔）
python3 <site-ops-bundle路徑>/scheduled-tasks/gulicalc_data_consistency.py --root <repo路徑>
```
如果手上沒有這支腳本，至少手動 `curl https://gulicalc.com/api/etf-dividends` 跟該標的自己的頁面表格對一次。

## 規則 2：不要寫死會隨股價漂移的即時殖利率

2026-07-30 已經在全站做過一輪修正（commit `ee28153`、`11b6614`），原則是：

- **單一標的的陳述句** → 寫「配息金額」（不會過期），不要寫裸的「殖利率 X%」
- **跨標的比較句** → 可以留殖利率，但一定要附「配息金額 + 股價」當基準，否則跨檔比較會誤導
  （配息少的可能殖利率反而高，光看金額會判斷錯）
- 教學公式、選股門檻、歷史年度數據、算式範例 → 不受此規則限制，本來就不是即時數字

細節見 `[[feedback_no_hardcoded_volatile_numbers]]`（另一裝置若無法讀取這份記憶，以本節文字為準）。

**如果你的自動更新腳本會重寫文章內的殖利率描述句，請確認它只更新「數字」，不要把句型改回裸殖利率格式。**
（2026-08-03 確認過一次沒有被改壞，但這是持續性風險，每次自動更新後都該抽查。）

## 規則 3：改動前後都要做的事

**改之前：**
1. `git pull` 到最新，不要在落後遠端的狀態下開始改——本文件寫成的當下就抓到本機落後遠端 7 個 commit，
   包含另一裝置當天對 006208 的修正，如果沒先 pull 就動手，很容易做出跟對方衝突或重工的修改
2. 看一下最近幾筆 `git log`，尤其是不是自己那個 git identity 推的 commit，了解對方剛做了什麼

**改之後：**
1. Commit message 要講清楚「改了什麼」「為什麼改」「查證方式」——不要只寫「fix data」
2. 如果是資料類修正（股價/配息/頻率/殖利率），在 commit message 或這份文件底下的「已知問題」區塊留一筆記錄，
   讓對方下次 pull 下來能看到脈絡

## 這份文件放在這裡的原因

之前的協調紀錄（change-log、實驗紀錄）都存在單一機器的本機路徑（如 `~/Desktop/.../change-log.md`），

兩邊 `git pull` 就都看得到，這是目前唯一能讓雙方真正對齊的地方。

如果你們決定要換一套更完整的協作機制（比如共用一份雲端的 change-log），
